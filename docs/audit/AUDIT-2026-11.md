## 3. P1 — YUQORI

### P1-1. Proxy ortida rate-limit va IP noto'g'ri ishlaydi

**Dalil:** `backend/src/app.ts:29` — `Fastify({...})` da `trustProxy` yo'q (butun `src`da topilmadi). `auth.route.ts:42` — IP `x-forwarded-for` sarlavhasidan qo'lda olinadi. `app.ts:54` — rate-limit Redis store'siz. `docker-compose.prod.yml` — backend `4000:4000` hostga ochilgan.

**Xavf (ikki tomonlama):**
- nginx/Railway ortida `request.ip` = proxy IP'si. Login limiti (30 urinish / 15 daqiqa) **barcha foydalanuvchilar uchun umumiy** bo'lib qoladi: ertalab 30 agent kirsa, qolganlar 429 oladi. Hujumchi esa butun kompaniyani login'dan bloklay oladi.
- `x-forwarded-for`ning birinchi qiymatini mijoz o'zi yozadi — login alert va audit'dagi IP soxtalashtiriladi.
- PM2 cluster'da limit har bir jarayonda alohida sanaladi.

**Tuzatish:** `trustProxy`ni aniq hop soni yoki proxy IP'lari bilan yoqing; hamma joyda `request.ip` ishlating; rate-limit'ga Redis store bering; kalit = `ip + tenant slug + login`; backend portini hostga ochmang.

### P1-2. Access token 24 soat yashaydi va bekor qilinmaydi

**Dalil:** `auth.service.ts:25` — `ACCESS_TOKEN_TTL = "24h"`. `auth.prehandlers.ts:42-76` — `jwtAccessVerify` bazadan `is_active`ni faqat `APP_ACCESS_ENFORCED_ROLES` (dala rollari, collector, auditor) uchun tekshiradi. `requireRoles()` rolni JWT ichidan oladi. `frontend/lib/auth-store.ts` — `accessToken` `localStorage`ga (`savdo-auth`) yoziladi.

**Xavf:** ishdan bo'shatilgan yoki roli pasaytirilgan admin/operator 24 soatgacha to'liq huquq bilan ishlayveradi. XSS bo'lsa, token o'g'irlanadi va 24 soat amal qiladi.

**Tuzatish:** access TTL 10–15 daqiqa; JWT'ga `sid` (sessiya id) yoki `tokenVersion` qo'shib, Redis keshi orqali har so'rovda tekshirish; web'da access token faqat xotirada (HttpOnly refresh cookie allaqachon bor); web javobida `refreshToken`ni body'da qaytarmaslik.

### P1-3. Refresh token: qayta ishlatishni aniqlash yo'q

**Dalil:** `auth.service.ts` `refresh()` — bekor qilingan token 30 soniyadan keyin kelsa shunchaki `INVALID_REFRESH` qaytadi, token "oilasi" bekor qilinmaydi; yangi token yaratish va eskisini bekor qilish tranzaksiyasiz. `JWT_REFRESH_SECRET` env'da majburiy, lekin kodda ishlatilmaydi.

**Xavf:** o'g'irlangan refresh token bilan hujumchi va egasi parallel yashayveradi — o'g'irlik aniqlanmaydi.

**Tuzatish:** `family_id` ustuni; eskirgan token qayta kelsa butun oilani bekor qilish + login alert; `$transaction`; ishlatilmaydigan `JWT_REFRESH_SECRET`ni olib tashlash.

### P1-4. Login himoyasi zaif

**Dalil:**
- hisob bo'yicha bloklash yo'q (`failed_login`/`lockout` topilmadi) — faqat IP limiti
- `staff.import.kinds.ts:437` — import qilingan xodimlarga ma'lum standart parol; majburiy almashtirish mexanizmi yo'q (`must_change_password` topilmadi)
- `mobile.schemas.ts:123` — yangi parol `min(6)`, murakkablik talabi yo'q
- 2FA yo'q
- foydalanuvchi topilmasa `bcrypt.compare` chaqirilmaydi → javob vaqti orqali login mavjudligini aniqlash mumkin; tenant topilmasa 404, parol xato bo'lsa 401

**Tuzatish:** login bo'yicha progressiv kechikish; `must_change_password` bayrog'i; minimal 8–10 belgi; admin va moliya rollari uchun TOTP; foydalanuvchi topilmaganda ham soxta xesh bilan `bcrypt.compare`.

### P1-5. Davomat terminali endpoint'i

**Dalil:** `backend/src/modules/tabel/tabel.route.mobile.ts:235` — `POST /api/:slug/mobile/attendance/device-ingest` JWT'siz. Qurilma tokeni bo'lmasa `pairing_code` (body yoki **query string**) bilan ham o'tadi; `revoked` bo'lmagan har qanday qurilma mos keladi. `body.user_id` ishonchli deb qabul qilinadi. Rate-limit yo'q.

**Xavf:** pairing kodni bilgan (yoki tanlab topgan) odam istalgan xodim nomidan "keldi/ketdi" yozadi — bu to'g'ridan-to'g'ri oylik hisobiga ta'sir qiladi.

**Tuzatish:** pairing kod bir martalik va qisqa muddatli bo'lsin, faqat tokenga almashtirish uchun; ingest faqat token bilan; query'dan kodni olib tashlash; rate-limit; `user_id`ni body'dan qabul qilmaslik.

### P1-6. Fayl yuklash: xotira va tur tekshiruvi

**Dalil:** `app.ts:40-49` — global multipart limiti kamida **512 MB**. `lib/storage.service.ts` `storagePut()` — butun fayl `Buffer.concat` bilan xotiraga yig'iladi. Butun backend'da `mimetype`/magic-byte tekshiruvi 0 ta. PM2 konfigda `max_memory_restart: 512M`.

**Xavf:** bitta katta yuklash jarayonni OOM qiladi — autentifikatsiyalangan har qanday foydalanuvchi API'ni yiqita oladi. Rasm o'rniga istalgan fayl yuklanadi.

**Tuzatish:** global limit 10–32 MB, katta limit faqat aniq marshrutlarda; S3'ga oqim bilan (`@aws-sdk/lib-storage` `Upload`); magic-byte tekshiruvi; rasmlarni `sharp` orqali qayta kodlash.

### P1-7. Buyurtmada ombor qoldig'i poygasi (oversell)

**Dalil:** `orders/domain/order.create-tx.stock.ts:29` — mavjudlik `tx.stock.findMany` bilan o'qiladi, keyin `reserved_qty: { increment }`. Shu papkada `FOR UPDATE` 0 ta; butun backend'dagi 131 ta `$transaction`ning birortasida `isolationLevel` berilmagan (standart READ COMMITTED).

**Xavf:** ikki agent bir vaqtda oxirgi 10 donani buyurtma qilsa, ikkalasi ham tekshiruvdan o'tadi — zaxira 20 bo'ladi.

**Tuzatish:** tekshiruvdan oldin `SELECT ... FOR UPDATE` (qatorlarni `product_id` bo'yicha tartiblab, deadlock bo'lmasligi uchun) yoki bitta atomar `UPDATE ... WHERE qty - reserved_qty >= $need` va ta'sirlangan qatorlar sonini tekshirish. Bazada `CHECK (reserved_qty >= 0)`. Parallel so'rovli integratsion test yozing.

### P1-8. Cron'lar API jarayonida va takrorlanadi

**Dalil:** `backend/src/index.ts:41-58` — 9 ta cron `setInterval` bilan API jarayonida yoqiladi; taqsimlangan lock faqat `payroll-cron.ts`da. `ecosystem.config.cjs` — `instances: "max"`, `exec_mode: "cluster"`. `scripts/docker-start.sh` — worker va API bitta konteynerda `&` bilan.

**Xavf:** har bir instans buyurtmalarni avto-yopish, narx jadvali, to'lov qaytarish, konsignatsiya yopish cron'larini alohida yuritadi — takroriy yozuvlar va poyga. Worker yiqilsa, konteyner buni sezmaydi.

**Tuzatish:** BullMQ allaqachon bor — cron'larni repeatable job qilib worker'ga ko'chiring; worker alohida konteyner (`Dockerfile.worker` mavjud); o'tish davrida har bir cron'ga Redis `SET NX PX` lock.

### P1-9. Yozuv API'larida idempotentlik yo'q

**Dalil:** `Idempotency-Key` backend, frontend va mobil'da topilmadi; "idempotency" faqat `stock/supplier-*` fayllarida. Mobil `sync_engine.dart` oflayn navbatni qayta yuboradi va `queue_id` jo'natadi.

**Xavf:** tarmoq uzilganda javob yetib kelmasa, qayta urinish ikkinchi buyurtma yoki to'lovni yaratadi.

**Tekshiring:** backend `queue_id` bo'yicha dublikatni rad etadimi. Agar yo'q bo'lsa — mijoz tomonda UUID yaratib, `(tenant_id, client_uuid)` unique indeks bilan buyurtma, to'lov va qaytarishlarga qo'shing.
